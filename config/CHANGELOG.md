# Settings changelog

Each change to config/locked.yaml gets a new tag and a dated line here, written before the run that uses it.

- 2026-09-29 - prereg-v1: first locked settings.
- 2026-09-29 - clarification, no settings change: each of the 22 untyped slice neurons is its own cell type in the model (1,224 types, 41,186 type pairs), as the guide's Phase 3 says. The Sep 25 gate numbers (1,203 / 41,029) counted them as one type. They are a mix of brain, nerve-cord, descending, ascending and motor neurons, so one shared time constant and bias would have no biological basis.
- 2026-09-29 - data, no settings change: 127 training songs excluded via config/excluded_songs.txt, before any training. 125 have a drum part note-for-note identical to a validation or test song's (83 such songs: 52 validation, 31 test); the training copies go so validation and test stay the official Slakh splits. The other 2 (Track00358, Track00739) have only auxiliary percussion, so no kit hits. Training drops from 1,289 to 1,162 songs (88.9 to 79.9 hours). 8 drum parts shared between validation and test are left alone; the gate checks only against training.
- 2026-09-29 - prereg-v2: training settings locked before any real training run. Adds the model's time-constant range and readout initialisation, the ear, the loss, the training loop (Adam 1e-3 with cosine decay, batch 8, gradient norm 1.0, whole-clip backprop, 1,000 BabySlakh steps, validation every 500) and the silence test. All values are those already in the code, so nothing the stability, cost or memorisation checks measured changes. Full-set steps stay open until the cost is known and get their own tag.
- 2026-09-29 - prereg-v3: readout normalisation, before any real training run. The memorisation check (250 steps, stopped) plateaued at loss 0.4932 against 0.4934 for the best output that ignores the audio, with every F1 near 0. Untrained motor-neuron rates vary by about 0.001 over time, so with readout weights near 0.01 the hit output moved by about 0.0001 when it needs to move by 1-3, and Adam at 1e-3 cannot grow the weights enough within 3,000 steps. Each readout motor neuron's rate is now standardised (mean and spread from 16 training clips through that network untrained, spread floored at 0.001) before the readout; the real network and each control get their own. Nothing else changes; the network's own activity, and so the stability result, is unaffected.
- 2026-09-30 - prereg-v4: random controls, before any real training run. The prereg-v3 degree-preserving swaps ran across the whole slice, so every control got 561-614 direct ear-to-motor-neuron connections (the real slice has 0; readout motor neurons one hop from an ear instead of 2-3) and reciprocal connections fell from 11.4% to 1.6%, lowering the largest eigenvalue from 731 to about 270. Both made the controls easier to train for reasons unrelated to the wiring: in memorisation, control 1 was ahead on every drum (F1 at step 1,500: kick 0.78 against 0.53). Swaps now stay within neuron classes (ears; interneurons 1 hop from an ear; interneurons 2 or more hops; motor neurons; hops measured on the real slice) and reciprocal pairs swap only as pairs, so each neuron keeps its connection counts per class of partner and the number of reciprocal pairs is unchanged. Each neuron still keeps its exact output synapse total and under 10% of real connections survive, as since prereg-v1. Checked on seeds 1-2 before building: no ear-to-motor connections, the real 2-3 hop layering, about 7% of real connections kept. Not matched, on purpose: loop strength. The largest eigenvalue stays 265-295 against the real 731, because the real network's strongest loops are a few heavy reciprocal circuits (such as around the wing motor neurons), which are part of the wiring under test. With each network scaled to its own critical gain, the real network's connections start about 2.5x weaker; this is reported with the results, not removed. (An earlier prototype that reported 479-515 moved synapse counts between neurons, breaking the output totals.) Seeds, swaps per connection and everything else unchanged. Details: reports/prereg-v4-controls-proposal.md.
- 2026-09-30 - note, no settings change: prereg-v4 controls built (reports/controls_report.json). Largest eigenvalues for seeds 1-5 are 295, 265, 284, 412 and 303 against the real 731; the prereg-v4 line's "265-295" came from seeds 1-2 only. Every control keeps 7.2-7.3% of real connections, 11.4% reciprocal connections and the real network's hop distances from the ears to each drum's readout.
- 2026-09-30 - prereg-v5: memorisation check, before any real training run. memorise.py now lowers the learning rate to 0 on the locked cosine schedule over its 3,000 steps (training.make_schedule, the one train.py uses); it had kept 1e-3 throughout. In the prereg-v3 runs the loss rose on 36% (real) and 47% (control 1) of the last 1,000 steps, with step-to-step jitter 19-29 times the underlying improvement. The check's own settings (4 songs x 2 clips, clip seed 7, 3,000 steps, a check every 250, F1 >= 0.9 on kick, snare and closed hi-hat) move unchanged into locked.yaml's new memorisation section; --steps/--songs now make a trial run marked as not the locked check. Measurement only, no training change: the check records each step's learning rate and gradient size before clipping, the size of each drum's readout inputs at each check (and for the untrained network), and the final weights. Readout scaling and readout width are unchanged; the measurements that would justify changing them (readout input size above 5; snare or closed hi-hat failing mainly on recall) are set in reports/prereg-v5-training-proposal.md before the next run. training.py changed (make_schedule, gradient size), so scripts/check_cuda_graph.py must be rerun before the recorded step is used again.
- 2026-09-30 - implementation, no settings change: the network forms its connection-matrix gradient once per clip (one multiply over all frames) instead of once per frame. Profiling (reports/profile_step.json) showed the per-frame dense gradients and their running total took most of a training step (matrix multiplies 2.87 s and in-place adds 2.38 s of 6.10 s GPU time). Same quantity, added in a different order: the forward pass is identical, and the check (scripts/check_cuda_graph.py, third part) requires every gradient to be at least as close to a float64 per-frame reference as the float32 per-frame one, within 1% of its error. On the CPU (2 clips, 1,000 frames) overall gradient error was unchanged (8.4e-7) and the connection dials' error fell from 4.0e-7 to 1.6e-7. The first GPU check of it failed: the stored per-frame rates were kept with their autograd links, so each step's graph referenced itself and was never freed (ordinary steps slowed to 12.8 and 23.2 s, and recording failed on a stale reference from warm-up). They are now stored detached; a test checks that a step's graph is freed. The second GPU check passed both recording parts (recorded step 3.12 s against 5.24 s) but failed the accuracy rule, which is unchanged: the connection dials' gradient was 9.4e-7 from the float64 reference against 6.0e-7 per frame, because one multiply adds each entry's 25,600 terms in one float32 chain. It is now done in blocks of 50 frames (400-term chains) whose results are added in float64; in a simulation of float32 chains the errors were 1.0e-6 per frame, 2.5e-6 one multiply, 3.1e-7 in blocks.
