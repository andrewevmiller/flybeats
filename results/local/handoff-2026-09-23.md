## What this session found and fixed

### 1. The queue as committed could not have run a single arm

Found by running it on tiny throwaway configs before trusting it with the
night (only `-WhatIf` had ever been run):

- **It died on the first stderr line.** Windows PowerShell 5.1 turns each
  stderr line of a redirected native command into an ErrorRecord, and under
  `$ErrorActionPreference = "Stop"` the first one ends the script. torch prints
  a sparse-CSR `UserWarning` seconds into every run. Reproduced in isolation,
  then fixed: stderr is folded into the log as plain text (`Invoke-Py`).
- **It logged into a directory it had not created yet**, so on a clone that
  had never run the queue — this one — the first log line threw.
- **It never probed the baseline.** `SUMMARY.txt` listed `velocity_probe_cpu`
  first, but the loop only probed the three arms, so the baseline section
  would always have read `(no probe)`.
- **An interrupted run counted as finished.** `best.pt` is written after
  epoch 1, and presence of `best.pt` was the "already trained" test. A run now
  counts as done when `history.json` holds every configured epoch.

Also added: a lock file (a second copy refuses; a stale lock from a dead PID
is cleared), `-StartAt HH:mm` (preflight immediately, train later),
`plan.json` and `DONE_<arm>` markers, and the new arms ordered first so a
night cut short still yields the new information. All paths exercised on
three 2-epoch configs, including the lock refusal, the stale lock, the skip
of completed arms, and a detached `Start-Process` launch. The POSIX twin
`run_velocity_queue.sh` still has the baseline-probe gap; it was not touched.

### 2. The per-arm budget was 2.5x too pessimistic

One epoch at 24 + 24 clips of `velocity_lin_cpu`: **53.8 s at 4 threads,
45.3 s at 8**, identical metrics to four places (onset F 0.1809, loss 0.9666).
The queue now defaults to 8 threads. Scaled to 256 train + 120 val clips that
is ~7 min/epoch, ~1.5 h/arm — not the ~4 h the 21 Sep handoff budgeted.
(The machine is on the **Power saver** plan; left alone, as it is a system
setting, but it probably costs throughput.)

### 3. The two smoke-test failures from 15 Sep §6 are fixed

- `cuda_smoke.check_bf16` compared two runs over different data. One line —
  `T.reseed_loader(batch, 0)`, which the test suite already had — takes the
  "drift" from **1.756 to 0.009**.
- `StreamingDrummer` defaulted to CPU whatever device the model was on, so
  nothing that streams could run on a GPU. It now takes the model's device.
  New GPU test: `test_streaming_runs_on_the_models_device`.

`cuda_smoke.py`: **5 passed, 0 failed** (was 3/2). `pytest -q` (GPU tests
included, with permission): **197 passed** — 192 CPU + 5 GPU.

### 4. Live latency at the 30k tier, CPU against GPU

15 Sep open item 2, blocked until the streaming fix. `scripts/stream_latency.py`,
untrained 30k model, 20 ms blocks, 50 per cell →
`results/local/streaming_latency_30k.json`:

| device | threads | speed 1 | speed 2 | speed 4 |
|---|---|---|---|---|
| CPU | 1 | 50.6 ms (p95 70.6) | 72.4 | 132.4 |
| CPU | 8 | 24.8 ms (p95 27.2) | 42.0 | 93.5 |
| GPU | – | **4.6 ms (p95 5.4)** | 7.1 (p95 9.4) | 10.2 (p95 12.7) |

**The 30k tier cannot play live on this CPU at any thread count; on the card
it has 4x headroom at speed 1 and still fits at speed 4.** So a live 30k
bundle means a GPU at the listener's end, or the 10k tier on CPU.

### 5. `runstat.ps1` draws the queue's progress

`powershell -File scripts\runstat.ps1 [-Watch]` now ends with an overall bar
in epochs, a per-arm line, the measured s/epoch and an ETA.

Fails the A′ bar: two classes significantly negative, and the head is *more*
compressed than the cloud baseline's (0.084), not less. Removing the sigmoid
did not unpin the head.

**A methodological catch that applies to every A′ arm, cloud ones included:**
`best.pt` is saved at the best val onset F, and the probe reads `best.pt`.
Here that is **epoch 2 of 12**, while the per-epoch `velocity_r` kept climbing
(+0.055 at epoch 2, +0.181 at epoch 10, +0.129 at epoch 11). So the per-class
intervals compare each arm at whichever epoch its *timing* score peaked, which
is itself noisy (the 16 Sep threshold-selection problem), not at the end of
training. `history.json` keeps the class-mean `velocity_r` for every epoch, so
arms can at least be compared on that at matched epochs; a per-class
comparison at the final epoch needs `train.py` to also save `last.pt`. Left
alone overnight so all four arms run identical code.
