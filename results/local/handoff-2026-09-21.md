## Start here: two decisions, and nothing expensive should run before them

Neither is a measurement. Both change *what the Phase D campaign measures*, so
running the campaign first means running it twice.

**1. The primary metric.** `evaluate` reports onset F at the best of ten
thresholds, chosen on the split it scores. In the B=4 pilot that selection was
worth +0.008 to the real arm and +0.093 to the rewired draws — larger than the
gap between the arms, so the ranking was decided by the selection rather than
by the topology. The honest options are to select the threshold on a held-out
split and report on val, or to fix one operating point for every arm and
publish the curve beside it. `onset_f_curve` is now persisted on every
evaluation, so either can be reconstructed from runs already done.
Full argument: `2026-09-16-threshold-response.md` §3 and §8.1.

**2. Do `gru` and `shortcut` get the genre tonic?** They accept it and discard
it. Measured on the 2k fixture, switching `style_id` moves the real arm by
2.8e-04 and those two by exactly 0.0. So they differ from the real arm in two
ways rather than one, and any deficit they show is partly missing conditioning
rather than missing topology. Arguable either way — the tonic is injected into
a named population and a GRU has no pC1 — but not arguable that it should be
silent. Changing it redefines an arm.
Detail: `2026-09-21-tier1-and-the-broken-venv.md` §4.

A third, smaller one, already costed: **B=3 null draws cannot produce a
significant result.** The floor on a one-sided rank p is 1/(B+1) = 0.25.
p ≤ 0.05 needs B ≥ 19, which at the spread run's measured 1h58m per draw is
~37 GPU-hours for one null arm at pilot scale — more than the current
31–53 h campaign estimate assumes.

## Traps specific to this machine

- **Ask before using the GPU.** The owner asked for that explicitly on
  21 September, and it applies to `torch.cuda` work of any size, not just
  training runs.
- **Never run two training jobs at once.** The documented collapse is 76 s →
  1,415 s per epoch: torch takes a thread per core in each process and the
  oversubscribed threads spin. `scripts/runstat.ps1` answers "is one already
  running" in one screen.
- **The venv can stop matching its own packages.** It was rebuilt with Python
  3.14 over a 3.12 `site-packages` on 16 September, and every run for five days
  died at `import torch` with a message about torch. `bootstrap_local.py` now
  catches it; if you see that error, run
  `py -3.12 scripts\bootstrap_local.py --check` first. The rebuild that fixes
  it is `...\Python312\python.exe -m venv .venv`, which keeps site-packages.
- **`python` is not the project's Python.** Bare `python` here is 3.14 with a
  CPU-only torch; the project is `.venv\Scripts\python.exe`, 3.12 with
  `2.14.0+cu126`. A sweep started with the wrong one runs on CPU and *reports*
  `device cpu` rather than failing.
