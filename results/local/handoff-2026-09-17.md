## Finding 1 — the `*_cpu.yaml` configs are not CPU configs

`configs/velocity_probe_cpu.yaml` inherits from `v1_8piece_cpu.yaml`, which
inherits from `v1_8piece.yaml`, which sets:

```yaml
train:
  device: auto
  bf16: true
```

`device_of()` in `src/build.py` resolves `auto` to CUDA whenever it is
available. **So the moment a CUDA wheel lands on this machine, the Phase A′
velocity queue silently moves to GPU with bf16 autocast on.** Nothing in the
filename or the config says so.

Two consequences, both bad:

- **A′1 already ran on CPU.** A′2 and A′3 on GPU would not be comparable to it,
  and comparison against A′1's per-class bootstrap intervals is the entire
  purpose of the remaining arms.
- **bf16 is emulated here.** No hardware bf16 below compute capability 8.0;
  this card is Turing at 7.5. Autocast would cost and return nothing.

**Fix before running anything:** pin `device: cpu` in
`configs/velocity_probe_cpu.yaml`, so all three A′ arms stay on one device.

## Finding 2 — `scripts/run_velocity_queue.sh` cannot run on Windows

It uses `PY=.venv/bin/python` — the POSIX venv layout, where this machine has
`.venv/Scripts/python.exe` — and `pgrep`, which Git Bash does not provide. It
needs a PowerShell port, or WSL. Keep the bash version for Linux.

## Task order

### 1. Fix the torch wheel — ~15 min, the highest information per minute here

```powershell
py -3.12 scripts\bootstrap_local.py --index-url <from pytorch.org's selector>
```

Take the URL from pytorch.org's selector rather than a hardcoded one; the cloud
container cannot reach that domain to check which `cuNNN` builds torch 2.14
ships. Driver 616.56 and compute capability 7.5 are supported by every current
CUDA build, so whichever option the selector offers will work. `--index-url`
now forces the reinstall (`bfe0f17`) — without it the CPU wheel stays exactly
where it is and pip reports success.

Then:

```powershell
python scripts\cuda_smoke.py --config configs\v1_8piece.yaml
```

which needs the subgraph cache and the corpus on disk. **The number that
matters most is peak VRAM at the 30k tier against 6 GB.** It decides whether
Phase D is runnable on this machine at all, and therefore what R4 in
`RELEASE_ROADMAP.md` can assume. If it will not fit, the order is
`grad_checkpoint: true` → lower `tbptt_steps` → fall back to the 10k tier.

Settle bf16 the same evening: time one epoch each way and set `bf16: false` if
it is not faster. `torch.cuda.is_bf16_supported()` returns `True` on Turing by
emulation and is not evidence.

### 4. Run the queue overnight

It waits out any running job, trains A′2 (`velocity_lin_cpu`) then A′3
(`velocity_peak_cpu`) strictly sequentially, probes each checkpoint and writes
`SUMMARY.txt`.

**Budget ~4 hours per run, not the ~100 min in `ROADMAP.md`.** That estimate
came off cloud cores. This CPU measured roughly 2× slower per thread, with 16
threads buying only 1.5× over one — 11.5 ms against the cloud container's
4.5 ms on the same 10k fixture. The pair plus probes is an overnight.

**Never run two training jobs at once.** The documented collapse is 76 s →
1,415 s per epoch. Do not overlap step 1 with step 4 either.

## Reporting discipline

Per-class bootstrap intervals, never pooled point estimates. This analysis has
already misled once: the same checkpoint read `hat_open` as 0.37, then 0.18,
then 0.26 before its sampling was seeded, and a pooled correlation reported
~0.35 while the per-class picture was incoherent.

A′1's onset F — 0.2761 against a 0.3006 baseline — is one unseeded run and
cannot distinguish a real detection cost from run-to-run noise. **Do not quote
it until it has seeds.**
