# Red team on the Gate P2 memo

16 Nov 2026 · RT: a second Fable fork · attacked: `gate-P2-memo.md`, `P2-engine-report.md`, `S0-build-report.md`, `P0-decisions.md`, and the code they describe. Everything marked "ran" was rerun here; line numbers are from the committed sources.

Severity: **B** blocks Gate P2 as written, **F** must fix before P3 starts, **N** note.

1. **F. The engine emits NaN and Inf on a brain exported without cliff calibration, which is the exporter's default.** Memo section 3: "Gain sweep 1 to 50× with guard limits: never NaN or Inf". The guard limits exist only when `export()` is given `runaway=` (`exporter.py` line `"runaway": runaway or {}`), and `brainfile.cpp:98` enables the guard only if `meta.runaway.mean_rate_limit` is present; the CLI's `--no-cliff` path and every brain made by `export()` without clips (all of the test brains, the drift brain) have `runaway: {}`. Ran: `flybrain_render rt.flybrain --controls {"gain_scale": 50}` on a brain exported without clips: 394 frames, **120 frames with NaN in rates or probabilities (first at frame 43), 12 with Inf**, largest finite rate 1.4×10³⁸. The NaNs go to the snapshot tap, the recorder and (in P3) the sampler's velocities. `RunawayGuard::check` does trip on `!finite` after `frames` (20) bad frames even with no limits, so the engine recovers, but 20 frames of NaN and Inf went out first. Fix: a hard default ceiling and mean limit in the engine when the brain carries none (and the Cliff Meter showing "unmeasured" is not a substitute), and the Lab gain control refusing to go above 1× on an uncalibrated brain.

2. **F. The hit half of the parity contract is mostly vacuous on the synthetic brains, and the memo presents it as evidence.** The synthetic readout saturates: in the C++ test data, drums 1 and 3 sit at probability ≥ 0.999 for 399 and 370 of the 400 frames (`ref64`), so every frame of those drums is a plateau tie. Ran: of the "96/96 identical hits" (`ref64`), **50 are ambiguous under the memo's own rule**; `ref32` 28 of 74; `hist64` 31 of 77; in the 10-minute large run 359,867 of 960,000 frame-drums are ambiguous and PyTorch produced 18 hits in 10 minutes. Consequence: a decoder bug confined to ties is invisible to every C++-versus-reference hit comparison. Ran: patching the reference decoder's left comparison from `>=` to `>` (a tie bug) still gives `compare(...)['passes'] == True` with 0 unexplained differences. The Python decoder has an exact tie test (`test_streaming_decoder_equals_peaks_rule`); **the C++ decoder has none**: `test_core.cpp:34` and `test_engine.cpp:22,155` compare hits only through `unexplainedHitDiffs`, and the block-size, reset and gain-recovery checks compare the C++ decoder with itself. Fix: a C++ decoder unit test with constructed probabilities (plateaus, equality at the threshold, first frame, flush) against exact expected hits, and a synthetic model whose probabilities are not saturated (`make_model`: `c_hit` −2 with `mn_std` 0.01 puts two drums permanently on) so genuine peaks carry the contract.

3. **N (process). "Tolerances fixed before the first run" is not what happened.** P0 section "Parity tolerances (fixed before the first run)" and memo section 2 ("fixed in P0 before the first run and were not moved afterwards"). The session's transcript shows the order: a scratch script measured the reference engine against PyTorch (2×10⁻⁷ rates, 16 vs 7 hits in float64), then `parity.py` was written with the constants and the ambiguity rule, then `P0-decisions.md`. P0 itself cites that first measurement as the evidence for the numbers. The constants were not moved after the test suite existed, which is the defensible claim; the ambiguity rule in particular was designed in response to the first observed hit mismatch (the float64 plateau), not before it. Say so.

4. **F. `process()` sets FTZ/DAZ on the host's audio thread and never restores it** (`engine.cpp` `process`: `if (cfg.flushDenormals) setFlushDenormals(true)` with no restore; same in `stepFeatures`). In a DAW the audio thread is shared with every other plugin; changing MXCSR for the rest of the callback is a host-visible side effect (JUCE's `ScopedNoDenormals` exists precisely to restore). Fix: save and restore around the block, or leave it to the shell.

5. **F. Corrupted or mismatched brain arrays that leave the dynamics unchanged pass parity; the harness binds only where it should, but one of its arms does not bind at all.** Ran deliberate corruptions through `compare` on the small brain: one active connection's sign flipped (rate error 0.11, caught), one active neuron's alpha ×1.5 (caught), ear bands rolled by one (caught), all weights ×1.0001 (3.9×10⁻⁴, caught), bias +10⁻³ (caught), one readout weight ×1.01 (caught via probability), `mn_std` ×1.001 (caught via probability), one frame shift (caught). Also ran: a connection whose sender never fires, an inactive neuron's alpha and a band permutation that is a palindrome on this layout were not caught, as expected, so parity on one clip says nothing about weights that the clip never exercises; the laptop run needs the 50 clips the plan asks for, not 20 (the CLI default). The hit arm: in every corruption above, the hit differences were all "ambiguous" (0 unexplained) even with rate errors of 0.1 to 2.7, so hit identity added nothing; the rate and probability tolerances did all the work (see 2).

6. **N. Memo claims slightly ahead of the tests.** (a) "a `best.pt`-shaped checkpoint ... exports a **byte-identical** brain": `test_checkpoint_round_trip_exports_identically` compares arrays, `g` and the eigenvalue; the files differ (the `created` timestamp is in the hashed header), so "array-identical". (b) "every perturbation ... **changes the output** (rule H3)" holds in both suites (`test_engine.cpp:157`, `test_reference.py`), fine, but for `deafen` and `band_offset` the C++ check is `rp.rates != base.rates`, which a single-ulp change satisfies; H3 asks for a measurable change on a reference clip. (c) The S0 report's and memo's "compiles on Linux" is true; the memo's section 1 table says the S0 state is "compiles on Linux (compile check only)" and the README promises Windows and macOS steps that no one has executed. Fine as stated. (d) Section 3 attributes the sanitizer run, the bus stress numbers, the resampler alias figure and the CPU table to the fork's report; the chair reran ctest (8/8, Release) and pytest (45/45) only. The memo says this in one clause; it should list which numbers are first-hand.

7. **F (S0, the owner would misread observation 4).** `plugin/s0/README.md` line 68: "the clicks should land 200 ms **late** relative to the bass (they are not delayed, so they show the true lateness)". Wrong direction. The pass-through is delayed by 200 ms and the click is not, so the click always leaves the plugin about 200 ms *before* the delayed bass. With compensation on, the host shifts the plugin's output 200 ms earlier: the pass-through lines up with the metronome and the clicks land about 200 ms **early** against the metronome. With compensation off, the clicks are on time against the metronome and the pass-through is 200 ms late. The discriminating observation is clicks against the metronome, not clicks against the pass-through. Rewrite step 2; the effect's code (`EffectProcessor.cpp:133-142`) does what the report says, the README's expectation is the inverted part. Also `applyLatency()` calls `setLatencySamples` from `processBlock` (line 72-77, called at 84) when the parameter changes; JUCE's VST3 wrapper tolerates it but some hosts re-query latency only at (re)activation, so the owner should set the latency choice *before* pressing play and note whether FL updates without a reload.

8. **N. `Core::setControls` cancels every in-flight injection on any control swap** (`network.h` `setControls`: `active.clear()` then re-adds the new block's injections with `frames > 0`). A threshold or band-offset change while a Tickle is running stops the Tickle silently, and re-sending the same block restarts injections whose `startFrame` is −1 from scratch. Reference engine: `set_controls` replaces `c.inject` the same way, so parity holds, but the Lab semantics are surprising. Decide and document before P3b.

9. **N. Hits dropped silently at `maxEvents`.** `publishDecided` writes an event only `if (h && nEvents < maxEvents)`; hits beyond the caller's buffer are kept in the snapshot but never counted or flagged. A shell passing a small event array under a long block (4,096 samples at 48 kHz holds 13 frames × 8 drums) could lose hits without knowing. Return a dropped count or saturate loudly.

10. **N. Checkpoint-agnosticism, what survives a reading of the exporter against the real slice.** Nothing found that assumes the synthetic layout: `ear_idx/ear_band` come from `FlyNet` itself; `motor_group`, `side` and `drum` maps tolerate `None`; duplicate edges are refused; `fixed` from the checkpoint is checked bit for bit against the slice's signs, so a checkpoint from the wrong slice (control vs real, same sizes) fails loudly; shape mismatches fail in `load_state_dict(strict=True)`. Two soft spots: (a) `cfg["training"]["hit_threshold"]` is baked in at export, so a brain carries the threshold of the `locked.yaml` on the laptop that day, and nothing records which tag; `locked_version` is in meta, good enough if the CLI's provenance is kept. (b) `verify_brain` and `hops_from_ears` loop per neuron in Python; fine at 3,326, slow at 10×, irrelevant now.

11. **N. Runaway limits are consistent but coarse.** `runaway_limits` = `bound_factor` (50) × the mean-over-time of the mean-over-neurons rate from the gain-1× silence test, held 20 frames; `RunawayGuard::check` compares the mean over all neurons of the clamped `r` (silenced ones included as zeros), and `silence_test` averages `mean_rate` over all neurons the same way, so the two agree. On the real network at 1×, `reports/stability.json` has peak 0.117 against music level 0.0305 (3.8×), far under 50×, so the guard cannot fire under normal music; at the Lab's highest safe gains it fires only after activity is already 50× normal for 100 ms. That is a last resort, not a protection for the user's ears: the output limiter (plan, risks table) still has to exist. `measure_cliff` can return `first_fail_gain: None` when nothing on the grid fails (the memo's "margin" is then `None`, shown as "unmeasured", fine) and the bisection's `resolution` is in gain units, so the stored "margin" is only good to ±0.02×, say so in the Cliff Meter copy.

12. **N (H-rules).** `export(capability=...)` accepts `"drum_capable"` from any caller; only the CLI pins `observation_only`. The file hash does not distinguish a chair-approved brain from one someone re-exported with the flag flipped. Before P3b, add a `gate_b` block (memo path, approver, date) that the plugin requires, or sign the header; until then the plugin must treat every brain as observation-only regardless of the flag. The Scoreboard default (`verdict: none`) is right. "DAW-corrected" and the Lab badge are P3 matters; nothing in the engine claims otherwise.

13. **N. Latency is a maximum, not a constant.** `latencyHostSamples()` = resampler delay + 2 hops. An onset early in a hop is known at the end of the next frame (≈2 hops); one late in a hop at ≈1 hop plus the fraction. Hosts compensate a constant, so hits will jitter by up to 5 ms around the reported value; feature #32 should show the range, not one number.

14. **N. `test_engine`'s and `test_cpp_engine`'s data are regenerated by `make_data.py` from the same `make_model` the reference uses, with the saturated readout of item 2; `pert_*` references come from `run_perturbed` with `make_data.py`'s own copy of `PERTURBATIONS` (the report says so). Two copies of the list will drift; move it to `parity.py`.

15. **N. Memory ordering and lock-freedom read as correct.** `TripleBuffer` (acq_rel exchanges, fresh flag in bit 2) and `SpscRing` (release on the producer's `tail`, acquire on the consumer's read) are standard and right; `Snapshot::copyFrom` on equal-sized vectors does not allocate; `Core::step`'s `erase` on a reserved vector does not allocate; `setControls` takes a mutex on the UI side only; the recorder's audio-side `push` is wait-free. Nothing on the audio path allocates, locks or throws after `prepare()`, matching the allocation-hook test. `Resampler::process` is called one sample at a time from `process()` with a 193-tap loop and two integer divisions per output: it is 4 % of a core now, but it is the obvious place a laptop's slower core shows first.

## Chair's answers

Each number answers the finding above. "Fixed" means in the commit that carries this file, with tests rerun (ctest 8/8, pytest 45/45).

1. **Fixed.** `RunawayGuard::prepare` now runs on hard defaults when the brain carries no limits (ceiling 10⁴, mean limit 10³, 20 frames; the same constants in `reference.py`), and `Engine::guardCalibrated()` tells the UI to show "unmeasured". New test 6b in `test_engine.cpp`: an uncalibrated brain at 50× gain, float and double, every snapshot and event finite, 16 resets. The Lab gain control refusing to exceed 1× on an uncalibrated brain is a P3b rule, recorded in the memo's section 6.
2. **Fixed.** `make_model` uses `mn_std` 0.05 (43 hits on the small clip, 40 genuine, no saturation); `compare` reports `genuine_hits` and the parity tests require at least 10; `test_core.cpp` gains an exact decoder test on constructed plateaus, threshold ties, a frame-0 hit and a plateau running into the flush, against the offline rule with no ambiguity allowance (5 expected hits, 0 mismatches). The large drift network's readout still saturates one drum; the memo now says its hit arm is weak.
3. **Accepted.** P0's heading and text now give the order of events: one scratch measurement, then the constants and the ambiguity rule, then the suite; nothing moved afterwards. The memo's "fixed in P0 before the first run" is replaced.
4. **Fixed.** `DenormalScope` saves the control word, sets FTZ/DAZ, restores on exit of `process` and `stepFeatures`.
5. **Accepted; partly fixed.** The CLI's default is now 50 clips. Parity on one clip cannot see weights the clip never exercises; P0's tolerance section now says so and lists the corruptions that were caught.
6. **Accepted.** (a) "array-identical" in the memo. (b) The C++ H3 check is an inequality; the Python suite's H3 check is the same. A measurable-change threshold per control is a P3b item for the control-effect tests, where the reference clip exists. (c) As stated. (d) The memo's section 3 now lists what the chair ran first-hand and what it took from the fork's report.
7. **Fixed.** README observation 4 rewritten: judge the clicks against the metronome; with compensation on they land about 200 ms early, with it off they are on time and the bass is late; set the latency before pressing play and note whether FL picks up a change without a reload.
8. **Accepted, not changed.** Documented for P3b: a control swap replaces the injection queue in both engines. The Lab's Tickle will send injections through their own queue or re-send them with the swap; decided when the UI exists.
9. **Fixed.** `Engine::droppedEventCount()` counts hits that did not fit the caller's array; test 6c covers a one-slot array over 4,096-sample blocks (32 dropped of 43, counted).
10. **Accepted.** `locked_version` and the locked-file hash are in provenance; the CLI keeps them. Nothing to change now.
11. **Accepted.** The guard is a last resort by design; the output limiter in the plan's risk table stays a P3a requirement. The Cliff Meter copy will state the ±0.02× resolution; `first_fail_gain: None` shows as "no cliff found up to 2×", not as a margin.

That is a record, not a signature: the memo's section 6 carries the rule that the plugin treats every brain as observation-only until a signed scheme exists, and the Scoreboard default stays `verdict: none`.

15. **Noted.** The resampler's per-sample call is the first place to optimise if a laptop core is short; measured at 4 % here, no change now.
